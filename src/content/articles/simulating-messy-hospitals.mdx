In my dissertation, five clients took part in every round, held the same data throughout and never failed. That made comparisons clean but unrealistic. Real hospitals go offline, join late, leave, and see different patients month to month. For my current work I've rebuilt the simulation around that.

## The federation

| Setting | Value |
| --- | --- |
| Hospital pool | 8 |
| Active at the start | 5 |
| Late joiners | 3, from round 4 onwards |
| Permanent departure | 1 hospital |
| Quorum | A round counts only if at least 2 valid updates arrive |
| Base partition | Dirichlet, α = 0.5, fixed for the whole run |
| Rounds | 50, with 5 local epochs each |

## The ten scenarios

Each round, a seeded random schedule applies one or more of these:

1. **Non-IID class distribution.** The base Dirichlet skew, at a varying severity.
2. **Partial class availability.** Some hospitals lose access to whole classes for the round.
3. **Unequal local dataset sizes.** Some hospitals train on a fraction of their data.
4. **Local class imbalance.** The class mix within a hospital is skewed further.
5. **Limited-data clients.** A hospital has very little data at all.
6. **Intermittent availability.** A hospital misses a round and returns later.
7. **New client joining.** A hospital appears partway through training.
8. **Permanent departure.** A hospital leaves and never comes back.
9. **Variable participation.** The number of hospitals per round changes.
10. **Different severities.** Each scenario can be mild, moderate or severe.

## The rule that makes it a fair test

The schedule is a function of the seed, not of the method. Two experiments with the same seed see the same hospitals, the same missing classes and the same shrunken datasets in every round. The code checks this: after both runs it compares the client lists and reported sample counts round by round, and fails if they differ.

## A loss that copes with missing classes

When a hospital's round data lacks a class, or is dominated by one, plain cross-entropy pushes its model towards predicting only what it sees. I use **logit-adjusted cross-entropy** (Menon et al., 2021): the log of the class prior is added to the logits during training.

$$
\mathcal{L} = -\log \frac{\exp\big(z_y + \log \pi_y\big)}{\sum_j \exp\big(z_j + \log \pi_j\big)}
$$

Common classes get a head start inside the loss, so the model doesn't need to inflate their logits, and predictions at test time, without the adjustment, are less biased towards them. Each hospital computes $\pi$ from its own round data, so the prior never leaves the hospital.

## Choosing a model without touching the test set

The client data is split into three folds, grouped so that identical files stay together. In each fold, the federated model is scored on that fold's validation images after every round, and the round with the best balanced accuracy is kept. The locked test set, 20% of all images, is used once per finished model and never for selection.

<Callout type="note">
None of this makes the simulation real. All "hospitals" are still slices of one public dataset, on one machine. What it does is stop a method from looking good only because every client always showed up with all its classes.
</Callout>
