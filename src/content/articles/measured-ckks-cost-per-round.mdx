A year ago I worked out from first principles roughly what a CKKS ciphertext should weigh. In my dissertation, encryption ran on a sample of each update as a prototype, so I never measured the real cost of a fully encrypted round. My current pipeline encrypts the whole update, and logs every byte and every second. These are the first numbers from a complete run on Kaggle's two Tesla T4 GPUs.

## What changed in the pipeline

The server now holds a **public** context with no secret key, checked at start-up:

| Item | Value |
| --- | --- |
| Polynomial degree | 8192 |
| Coefficient modulus | [60, 40, 40, 60] bits |
| Scale | $2^{40}$ |
| Values per ciphertext | 4,096 |
| Server's keys | Public context and relinearisation key only |
| Server can decrypt? | No, checked in code |
| Client key file | 0.70 MB |

Each client encrypts its sample-weighted model, $n_k W_k$, flattened into chunks of 4,096. The server adds ciphertexts and multiplies the sum by $1/\sum n_k$, a plain number, without ever decrypting:

```python
def secure_weighted_fedavg(server_ctx, encrypted_updates, sample_counts):
    total = None
    for update in encrypted_updates:
        chunks = [ts.ckks_vector_from(server_ctx, blob) for blob in update]
        total = chunks if total is None else [a + b for a, b in zip(total, chunks)]
    scale = 1.0 / sum(sample_counts)
    return [(chunk * scale).serialize() for chunk in total]
```

## The model

The client model in this run is a Tiny CNN with **74,508 parameters**, 0.298 MB in float32. At 4,096 values per ciphertext, that is $\lceil 74{,}508 / 4{,}096 \rceil = 19$ ciphertexts per update.

Two things are worth explaining.

**About 0.33 MB per ciphertext.** 6.296 MB over 19 ciphertexts is 0.331 MB each. My back-of-envelope figure a year ago was 0.39 MB uncompressed, so serialisation saves a little.

**The global model is smaller than the uploads.** Multiplying by $1/\sum n_k$ consumes one level: the ciphertext is rescaled and drops one of its 40-bit primes. Going from 140 bits of data modulus to 100 should shrink it to about $100/140 \approx 0.71$ of its size, and the measured ratio is $4.466 / 6.296 = 0.709$.

## Time

| Step | Time per round | Who |
| --- | --- | --- |
| Encryption | 1.047 s | All contributing clients together |
| Aggregation | 0.125 s | Server, on ciphertexts |
| Decryption | 0.040 s | One global model |
| A client's whole local fit | 26.6 s | For comparison |

## Error

Every round, the decrypted CKKS average is compared with a plaintext FedAvg of the same updates. The largest values over all rounds were:

| Measure | Value |
| --- | --- |
| Maximum absolute error | $2.07 \times 10^{-7}$ |
| Root mean square error | $2.76 \times 10^{-8}$ |
| Relative L2 error | $1.50 \times 10^{-7}$ |

For comparison, float32 itself has a relative precision of about $6 \times 10^{-8}$. CKKS's approximation error here is of the same order as ordinary floating point rounding, far below anything that would change training.

## How it scales

Size and encryption time both grow linearly with the number of ciphertexts, so with parameters. Applying the same 0.331 MB per ciphertext to my dissertation's 2.58-million-parameter models, at 629 ciphertexts, gives an estimate of about **208 MB per client upload**. That is an extrapolation, not a measurement, but it shows why a 74,508-parameter client model is worth the trouble.

<Callout type="key" title="The lesson I keep relearning">
Measure serialized ciphertexts. Estimating "encrypted size" from the plaintext model, which an early version of my code did, underestimates the payload by a factor of about 21.
</Callout>
